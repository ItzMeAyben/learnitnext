## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL path segment (subjectId) → decode → store/API lookup | Client-controlled id is decoded and used for data resolution |
| API response status → render control | The 404/200 contract from Plan 02 gates what renders |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Tampering | decodeURIComponent(subjectId) in both client pages | mitigate | try/catch → `name = ''` → `notFound()` — `/subjects/%` and `/pathway/%` render not-found instead of crashing with an unhandled URIError |
| T-05-02 | Tampering | subject.id interpolated into hrefs | accept | All hrefs via `encodeURIComponent` (specified per control); ids originate from the app's own store, never raw user input |
| T-05-03 | Information disclosure | unknown-id handling | mitigate | Client checks `res.status === 404` (explicit status, Plan 02 contract) rather than rendering whatever body arrives — removes reliance on the old fallback that returned WRONG data for probed ids |
| T-05-04 | Spoofing | subject pages | accept | No auth; single-user mock; nothing to protect |
| T-05-05 | Repudiation | navigation wiring | accept | Read-only screens; no mutations added |
| T-05-06 | DoS | client pages | accept | One list fetch + client find over 3 subjects; scrollIntoView is local |
| T-05-07 | Elevation of privilege | not-found path | accept | notFound() renders public UI only |
</threat_model>
